# Project agent memory

This repository is the People Domain for Bilibi. It builds only when
mounted in a Bilibi checkout at `apps/domains/people` (see `README.md`).
Read Bilibi's `AGENTS.md`, `apps/domains/AGENTS.md`, `apps/base/ui/AGENTS.md`
and `apps/base/ports/README.md` in that checkout first; they govern this
code and are not copied here. Entries below are this repository's own
rules: short "use this, not that" lines with the reason.

- Correct entries that work proves wrong; add new ones only by deliberate maintainer choice, never as routine task output.

## Architecture

- **No production users yet (until 2027-01-01).** Never build data imports, backfills, conversion of existing rows, or compatibility tables, columns or code paths; replace or drop them in a new migration. Development and walkthrough databases are disposable. After 2027-01-01 this rule no longer applies: ask the owner whether to extend it before relying on it.
- Mount a real copy (`git clone`), never a symlink, and commit and push only inside this repository: Askama and path dependencies resolve from the mount location, and the Platform's `apps/domains/Cargo.toml`, `apps/domains/src/lib.rs` and `Cargo.lock` change while mounted but belong to the Platform in their unmounted form (`discover-modules.py --check` refuses them committed). Never commit a lock file, a root `Cargo.toml` or a `[workspace]` here: discovery refuses the shape.
- Expose one small facade per module (`workforce/src/lib.rs`: `Workforce` with its record and input types, `ReadResult`, `WorkforceError` and the capability keys; `settings/src/lib.rs`: the menu outline) and keep the schema, SQL, validation and helpers in private modules, not `pub`: a deep module is the one place a rule lives, so a caller cannot bypass the capability check, the company lock or the validation by reaching a lower layer. A sibling reaches a module only through its facade, on an edge declared in both the descriptor's `dependencies` and the Cargo manifest, only where Bilimbi has the same edge (every module → `people/settings` and `people/workforce`; `leave` → `reference_data`; `performance` → `organisation`, `skills`; `progression` → `performance`, `skills`; `payroll` → `attendance`, `leave`, `claims`), never in a cycle. Organisation answers Workforce's position scan through the `people/organisation.positions` port, not an edge the other way.
- Never add a Cargo dependency, descriptor edge, port call or SQL reference to another Domain's container (Finance, Supply Chain, Factory, the People connector): each couples the two containers' composition or schema. Cross-domain flows publish Base domain events (`apps/base/events`: payroll's `run_approved`, claims' `request_approved` and `request_reimbursed`) inside the deciding transaction, and the People connector reads through the `people/workforce.directory` port.
- Use only meta-terms in Domain code: employee, employment, position, skill, course, session, policy, claim, leave type, pay item, provider identity. Currencies, countries, statutory packs, employment types, course and skill names are a company's data, never a code identifier, constant or default; the five employment statuses are the one fixed classification. No country or vendor pack and no sample rows: proofs create their own records in `fixtures/walkthrough` on a disposable database.

## Platform contracts

- Keep Bilimbi's IDs, keys and names verbatim: module IDs `people/<module>`, tables under `people_<module>_*` (Bilimbi's own names, `people_skill_*`, `people_positions`, …), capabilities under the Authz domain `people`, the menu IDs, labels, orders and icons, flash texts, confirmations and withheld-control sentences. They are persisted data and the parity reference. Declare every verb a capability key ends in that Base does not already declare (`reimburse`, `recommend`, `answer`, `generate`): the vocabulary refuses a key whose last segment no module declared.
- Authorize inside the facade through the Workforce `Authorization` helpers (`bilibi_people_workforce::authorization::{authorize, authorize_company, selectable_companies, allowed}`) with the scope it was handed, never Core's functions directly and never an actor, employee or company taken from a form: the helpers evaluate the capability now and the company axis through Core Company's `authorize_work_target`, so a revoked grant refuses the next operation, and a system principal (`bilibi_authz::SystemScope`) cannot reach them at all. In a self-service write resolve the signed-in employee on every call and re-prove it under the employment lock (`with_self_employee_lock`, PW1): an unlinked or relinked account must not act on its former employee.
- Make every write through `MutationBoundary` (`tx.mutate` returning each affected row as a `Change`, `json!({})` on the absent side so audit names it `created` or `deleted`), holding `bilibi_company::require_writable(.., lock = true)` first, never a bare transaction: a write that reports no `Change` cannot commit, and the company lock is what refuses an archived company and serializes a company's writes. Decide refusals with `tx.sql()` before `mutate`, and return them as typed `WorkforceError` variants or `FieldError`s with Bilimbi's sentences, never `Error::Forbidden`/`Error::Internal` from a live event: the live transport treats those two as fatal. An employment write takes the Core Affiliation proof inside the same transaction (`workforce/README.md`, "`create_employment`"), never a person or affiliation id trusted from input.
- Name every employee by the employment id (`people_workforce_employments.id`), never a Core Person, affiliation or account id: Bilibi has no Core Employee, and the employment row is the one durable employee reference every People table keys on. Read names and contacts through Core as `workforce/src/directory.rs` does (the Principal Directory for names, the Affiliation owner's read for work contacts), never by selecting `persons` or `person_affiliations`.
- Draw every list with the shared `FlexTable` on `ListState`/`ListColumns` with the table features Bilimbi enables on that page, including Bilimbi's hand-rolled `<ul>` and `<table>` lists; `ConfirmDialog` for every irreversible action with the selection held on the server; `forms::file_input` for files; `DOWNLOADS` for bytes; `PdfOwner` for PDFs; Base Settings with the `define!` editor capability for every operator value (`workforce/src/contributions.rs`). A page checks its capability again on every write-shaped event and the facade checks once more. Domains own no CSS or JavaScript: a class the Platform stylesheet lacks is a Platform change made with nothing mounted.
- Name a migration `people-<module>-NNN-<slug>` under the module's `migrations/`, declared in the descriptor, and add a new file for every schema change, never editing an applied one: the ledger records each file's SHA-256 and refuses a changed applied file. Bind and read a `date` column as text (`$n::text::date`, `to_char(col,'YYYY-MM-DD')`): the workspace's `tokio-postgres` has no date feature, and a Domain must not turn one on for every Platform crate.
- Keep `fixtures/walkthrough` the only fixture: an example-only crate that migrates a disposable database, installs the Platform fixture and creates records through the facades, never seed data, demo users or demo pages; prove behaviour in the running app, never with unit tests. It stays a workspace member through `workforce`'s `[dev-dependencies]` edge (Cargo adds path dependencies of members, and ignores one without a lib target, which is why it has `lib.rs` and a thin `main.rs`); never move it to `[dependencies]`. A slice keeps its proof and registration in its own `fixtures/walkthrough/src/<slice>.rs` file (`fixtures/walkthrough/README.md`), never adding calls or declarations to `lib.rs` or branches to `main.rs`: build discovery and the fixture registry collect it without shared-list merge conflicts.
- Document a module in its own `<module>/README.md`; this file and the root README take a line only when it is true for the whole Domain, because many slices run in parallel and shared files cause merge conflicts.
